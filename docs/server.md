# PokeFocus server (F2 + live administration)

Node + Hono API that owns every player's game state. The browser only sends intents (`POST /api/game/action`); the server runs the rules with the same engine (`src/engine`) through the pure reducer `src/game/actions.ts`, stores the result in PostgreSQL (PGlite in development) and returns the new document. Spec: `docs/F2-plan.md`. Contract: `src/game/protocol.ts`. Phase E (live content, events, admin panel) design: `docs/admin-plan.md`; how to operate it: `docs/admin.md`.

## Running

```bash
npm run dev            # Vite on 5173 + API on 8787 (tsx watch, DEV_TOOLS=1, PGlite in .data/pglite)
npm run dev:server     # API only
npm run dev:client     # Vite only (proxies /api → http://localhost:8787)
npm test               # unit + integration tests (in-memory PGlite)
npm run typecheck      # app, node scripts and server tsconfigs
npm run build          # tsc -b (incl. server) + vite build → dist/
npm start              # production: NODE_ENV=production, serves dist/ and /api from one origin
npm run db:generate    # new migration after editing server/db/schema.ts
npm run vapid          # print a fresh VAPID key pair for Web Push (writes nothing)
npm run pepper         # print a fresh PASSWORD_PEPPER (writes nothing)
npm run admin:role -- you@example.com admin   # set an account's role (see «Becoming admin»)
docker compose up --build   # PostgreSQL 17 + app on :8787
```

Migrations are applied automatically on startup (`drizzle-orm/*/migrator`), for both drivers. To start over in development, stop the server and delete `.data/`.

### Resource limits and load protection

Added after the load tests and the security audit (`docs/load-report.md`, `docs/security-audit.md` A1/A2):

- **Containers** (`docker-compose.yml`): `mem_limit` and `cpus` for `db` and `app` (`DB_MEM_LIMIT`/`DB_CPUS`, default 2g/2; `APP_MEM_LIMIT`/`APP_CPUS`, default 3g/2) and rotated logs (10 MB × 3). **Adjust them to the machine** (`free -h`, `nproc`): the sum of the memory limits must leave room for the OS; one container hitting its limit is restarted alone (`restart: unless-stopped`) instead of the kernel killing a random process.
- **SSE** (`server/routes/events.ts`): `MAX_SSE_PER_USER` (default 6; a new connection past it closes the player's oldest one, so several tabs work), `MAX_SSE_TOTAL` (default 10,000 per process, ~200 KB each; past it `503 server_busy`) and 60 new connections per player per minute.
- **Load shedding** (`server/app.ts`): `MAX_INFLIGHT` (default 400; 0 = off) API requests served at once; past it `503 server_busy` + `Retry-After: 2` at once instead of queueing behind a saturated pool. SSE, `/api/health` and `/api/admin/*` are exempt.
- **Game actions** (`server/routes/game.ts`): 120 per player per minute (`gameActionUser`), at most 3 in flight per player (`429 too_many_requests`), and the real weather of `start` is fetched **before** the transaction (it used to hold a pool connection and the player's row lock for up to 2 s).
- Ranking top and total of the global/country boards are cached (`LEADERBOARD_CACHE_MS`, 10 s in production).

### Load tests (`scripts/load/`)

Results and conclusions: `docs/load-report.md`. Nothing here ever touches production: the tool starts **its own** server (port 18787, `NODE_ENV=development`, clean environment: it does not read the project `.env`, uses a throw-away `PASSWORD_PEPPER`) against a **PostgreSQL 16 container** (`pfload-pg`, 127.0.0.1:55432, named volume `pfload-pgdata`), and removes both at the end (also on Ctrl-C). It has no `--url` option on purpose. Needs Docker (the `postgres:16` image is pulled the first time).

```bash
npm run load:smoke                                  # ~1 min: 40 users, checks every scenario works
npm run load:run -- --levels 100,1000               # real levels (default); also 5000, 10000, or any number
npm run load:run -- --levels 5000 --ramp 60 --hold 120 --think 10000
npm run load:report                                 # regenerate docs/load-report.md + docs/load-charts/*.svg from .data/load/results/
```

Flags: `--levels a,b`, `--users/--ramp/--hold` (override one level), `--think ms` (time between actions of a user, default 20000), `--study ms`, `--actors 0.1` (fraction that also studies), `--login-rate 0.002` (login probability per action), `--workers N` (load-generator processes), `--pg-port`, `--port`, `--pg-image`, `--min-mem-mb 1500` (aborts a phase if free RAM drops below), `--no-dev-tools`, `--keep` (do not delete the container).

Extra flags: `--tag name` (suffix of the result file/level), `--pg-stats` (loads `pg_stat_statements`; after each measured phase the 15 queries with the most total time go to `.data/load/results/<level>-queries.json` and the report prints a top-10 table per level; the counter is reset after sign-ups/seeding, so only the measured phase counts; the scenarios below turn it on by themselves, `--no-pg-stats` turns it off), `--no-report` (do not regenerate `docs/load-report.md` at the end; handy for smoke runs).

**Scenarios** (`--scenario steady|peak|event`, default `steady`). Result files are named `<users>-<scenario>[-big][-<tag>]`; the phase length is computed from the scenario unless `--hold` is given.

```bash
# Peak: 30 % of the connected users start a session within 8 s ("on the hour"); they claim ~--study ms later.
npm run load:run -- --levels 1000 --scenario peak --peak-pct 30
npm run load:run -- --levels 5000 --scenario peak --peak-pct 30 --peak-window 8 --recover 90
# Published event: everybody on SSE, an admin publishes a live event and, 25 s later, announces it.
npm run load:run -- --levels 5000 --scenario event
# Big database: 5,000 active users over 100,000 registered (sleeping) users; combine with any scenario.
npm run load:run -- --levels 5000 --big-base 100000
npm run load:run -- --levels 5000 --big-base 100000 --scenario peak
npm run load:run -- --levels 5000 --big-base 100000 --scenario event
```

- `peak`: `--peak-pct 30` (% of users in the peak), `--peak-at 20` (s after the ramp ends), `--peak-window 8` (s over which they start), `--recover 60` (s observed after the peak). Needs `DEV_TOOLS` (game clock via `x-dev-now`). The peak users are not "background actors"; the rest keep the normal mix. The report compares baseline / peak / after (req/s, p95 per second, errors, CPU, RAM, PG connections) and gives the seconds until the p95 is back to ≤ 1.5× baseline.
- `event`: `--event-at 25` (s after the ramp), `--event-gap 25` (s between publish and announce), `--recover 60`. The tool registers a throw-away admin (`admin@load.test`, role set by SQL in the temporary database), does `POST /api/admin/reauth` (sudo) with the test password, creates a draft event and publishes/announces it through the real admin API (`POST /api/admin/events/:id/publish|announce`). Every client reacts like the app (`content` → refetch `/api/content` + `/api/live-events`; `event_announce` → `/api/live-events`). Measured: SSE arrival delay p50/p95/p99 per notice (from just before the admin request is sent, so it includes the publish itself, shown separately), clients reached / connected, CPU/RAM/PG per 10 s window, and the requests it provokes (`react.*` rows). No `ADMIN_TOKEN` is involved.
- `--big-base N`: before the measured phase (once per run, after the sign-up phase) the database is topped up to N users with "sleeping" users by bulk SQL (`scripts/load/bigbase.ts`, `generate_series` in batches of 5,000, no API): same precomputed password hash as an active user, a player document copied from a real one and grown to 30 Pokémon (~28 KB), scores for the current and previous weeks/months (≈40 % / 25 % of them), ≈8 friends each and 10 sleeping friends per active user; then `ANALYZE`. Measured at 3,000 users: ~12 MB per 1,000 users in the container volume (so ~1.2 GB for 100,000; the copies compress better than real documents, so it is a lower bound) and ~1 s per 3,000 users to seed (extrapolated: about a minute for 100,000; not run at that size).

How it works: a user is registered through the real API (one scrypt each: the heaviest call), keeps its cookie, holds an SSE connection and loops over `GET /game`, `/leaderboard` (global/country/friends × week/month), `/friends`, `/content` (with and without `If-None-Match`) and `/config`; a fraction studies (`start` → `claim` → `dismissResults`) and a few log in again. Rate limits stay **on**: the server runs with `TRUST_PROXY=1` and every virtual user sends its own `X-Forwarded-For` IP. The server decides study minutes with its clock and the minimum session is 15 min, so studying users use `DEV_TOOLS=1` and the `x-dev-now` header to advance their own game clock (same reducer and transaction as production; `--no-dev-tools` disables actors). Resources are sampled every 2 s from `/proc` (server process), the container's cgroup (PostgreSQL CPU/RAM/net) and `pg_stat_*` (connections, tx/s). The load generator itself uses worker processes and `node:http` (no extra dependency).

## API notes for the client

All endpoints are under `/api`, JSON in and out, cookie `pf_session`. Errors are `{ error: code }` (sometimes with extra fields).

**Every non-GET request** must send `Origin` (browsers do) from `APP_ORIGIN` and `Content-Type: application/json` — also bodyless ones (`logout`, `DELETE …`, `accept`). Otherwise `403 bad_origin` / `415 json_required`.

| Status | Codes |
|---|---|
| 400 | `invalid_json`, `invalid_body` (+ `fields: string[]`), `invalid_scope`, `invalid_period`, `invalid_query` (bad query string), admin-only: `invalid_dates`, `invalid_effective_at`, `sim_too_big`, `range_too_large`, `empty_body`, grant errors (`empty_grant`, `too_many_items`, `unknown_item`, `invalid_amount`, `amount_too_large`) |
| 401 | `unauthorized` (no/expired/revoked session, or a wrong admin token), `invalid_credentials` (login: wrong password **or** unknown email) |
| 403 | `bad_origin`, `dev_disabled` (dev action without DEV_TOOLS), `wrong_password` (POST /auth/password, POST /admin/reauth), admin-only: `forbidden` (role too low), `forbidden_target` (support on a staff account), `elevation_required` (sudo mode needed) |
| 404 | `not_found`, `unknown_friend_code`, `unknown_content` (GET /content/:hash), `admin_disabled` (no `ADMIN_TOKEN` on the server) |
| 409 | game rule errors (see below), `email_taken`, `cannot_add_self`, `already_friends`, `already_requested`, `too_many_friends`, `too_many` (maintenance windows), admin-only: `too_many_drafts`, `not_draft`, `not_published`, `not_scheduled`, `not_editable`, `slug_taken`, `slug_locked`, `confirm_required`, `busy`, `in_use`, `uploads_full`, `not_locked`, `self_target`, `no_player`, `name_locked` / `country_locked` (PATCH /auth/me, with `unlockAt`; the client keeps it in `ApiError.body`) |
| 413 | `body_too_large` (> 64 KB; 512 KB admin content/events; 3 MB image upload) |
| 415 | `json_required`, `unsupported_type` (image upload) |
| 422 | admin-only: `validation_failed` (+ `errors`, `warnings`, `requiresConfirm`), `invalid_patch`, `unknown_image`, `invalid_image`, `image_too_small`, `image_too_large`, `animated_image` |
| 429 | `rate_limited` (+ `retryAfter` seconds; also the `Retry-After` header) |

Auth: `POST /auth/register` → 201 `{ user }`; `POST /auth/login` → `{ user }`; `POST /auth/logout` (no session needed) → 204; `POST /auth/logout-all` → 204; `GET/PATCH /auth/me`; `POST /auth/password { current, next }` → 204 (other sessions revoked, current kept); `GET /auth/sessions`; `DELETE /auth/sessions/:id` → 204. `PATCH /auth/me { trainerName?, country?, anonymousRankings? }` (at least one field, else 400 `invalid_body`) → `{ user }`; a new `trainerName` also renames the trainer inside the game doc (bumps the version, emits `game`).

- **Name and country lock (30 days).** `PublicUser` carries `nameChangedAt` and `countryChangedAt` (epoch ms of the last change, `null` = never changed since sign-up), stored in `users.trainer_name_changed_at` / `users.country_changed_at` (nullable `timestamptz`; migration `0003_account_locks_privacy`, so existing accounts start with `null` and their first change is free). Constants `NAME_LOCK_DAYS` and `COUNTRY_LOCK_DAYS` (30) in `src/game/protocol.ts`.
  - A *change* is a value different from the current one (country compared after upper-casing, name after trimming). Sending the current value is a no-op: it never fails, never starts a lock and never moves a timestamp.
  - A change is allowed while `now >= lastChange + 30 days`; otherwise **409** `name_locked` or `country_locked` with `{ error, unlockAt }` (`unlockAt` = last change + 30 days, epoch ms). Each field has its own lock.
  - The request is all-or-nothing: if any change in it is locked, nothing is applied (not even `anonymousRankings`). With both locked, `name_locked` is reported.
  - The check runs inside one transaction after `select … for update` on the user row, so two concurrent changes cannot both pass. `deps.clock()` is the time source.
  - `DEV_TOOLS=1` ignores the locks (same as the time-zone lock in `src/game/actions.ts`); a real change still stamps the timestamp.
- **`anonymousRankings`** (boolean, `users.anonymous_rankings`, default `false`, no lock) is returned in `PublicUser` by register, login, `GET /auth/me` and the PATCH response. See Leaderboard for what it hides.

Game: `GET /game` → `GameSnapshot`; `POST /game/action` with a `GameAction` → `ActionResponse` (`{ doc, version, serverNow, result }`). `serverNow` is the game time used (the dev clock when `x-dev-now` is honored).

- **`createPlayer`** takes no `trainerName`: the server passes the account's trainer name to the reducer (`ActionEnv.trainerName`).
- Reducer error codes (409): engine errors (`session_active`, `invalid_duration`, `empty_team`, `ThrowError`, `ChargeError` incl. the new `already_has_status`, `BoxError`, `UseItemError`, mission errors, `invalid_starter`, `no_active_session`, `invalid_times`) plus `no_player`, `player_exists`, `no_session` (pause/resume/cancel/claim/markNotified without a session, startBreak with no session yet), `paused` (claim while paused), `not_finished` (claim before `endsAt`), `already_finished` (pause or cancel after `endsAt`; a finished session must be claimed), `no_encounter` (nextWave/finishWaves without waves), `no_break` (endBreak), `already_claimed` (startBreak twice for the same session), `session_active` (startBreak during a session), `session_active_elsewhere` (database already holds an active study session for the user).
- `pause` while paused and `resume` while running are idempotent (200, no change but the version still bumps). `dismissResults`, `ackLevelUp` and `skipBreak` always succeed.
- `devFinishNow` is not an action: advance the dev clock (`x-dev-now`) past `timer.endsAt`.
- `claim.devFocusLabel` is ignored unless DEV_TOOLS=1 (then no screenshot labels = "no permission" focus value).
- `claim.soundProfile` (optional) `{ silence, music, voice, noise }`: microphone shares measured in the browser (audio never leaves the device). Each 0–1, sum ≤ 1.05, otherwise 400 `invalid_body`. Passed to `completeSession` in every mode (Flying/Psychic conditions, wild types).
- **`start`** looks up the real weather (Open-Meteo, no API key) and the reducer stores it on `activeSession.weather`; `claim` uses that for Fire/Water/Ice. Source: `profile.location` (a ~0.1° cell rounded by the client and again by the reducer; sent straight to the forecast API, no geocoding), else `profile.city` (geocoded). The lookup waits at most 2 s (a slower one keeps going and fills the cache for the next start); results are cached 30 min per cell / per city, failures 5 min (in memory only). Nothing detected → `weather: null` (no manual fallback). Group starts run the same lookup for each invitee, which is why the rounded cell lives in the profile instead of being sent with `start`. Rule shared in `src/game/weather.ts` (`resolveSessionWeather`). Tests inject a fake `fetch` (`createApp({ fetch })`).
- **`updateProfile.patch.location`** `{ lat, lon } | null` (lat −90…90, lon −180…180, else 400): only the rounded cell is stored; null clears it. No cooldown for location or city.
- **`setWeather`** (manual weather) is a dev action: 403 `dev_disabled` without DEV_TOOLS=1. With DEV_TOOLS=1 `profile.weather` overrides the detected weather; without it, it is ignored everywhere (also in old saves that still carry one, including `claim` of a legacy session without `activeSession.weather`).
- Week keys are the engine's (`weekKeyOf`: the local Monday, e.g. `2026-11-02`), month keys `2026-11`.

Config: `GET /config` → `ConfigResponse { devTools: boolean }` (public: no session, `Cache-Control: no-store`; `src/game/protocol.ts`). `devTools` is the server's effective `DEV_TOOLS` (always `false` in production, Docker, `npm start`): only then are `x-dev-now` / `x-dev-seed` honored and the `dev*` / `setWeather` actions accepted. The client reads it at boot; when it is `false`, the developer panel (`?dev`, Settings → Developer tools) shows a notice and hides its server-side controls (clock, finish session, items, weather, seed), drops a shifted dev clock, stops sending the dev headers and ignores the lock bypasses. If the request fails the client treats it as unknown and behaves as before (the server still refuses: `409 not_finished` on a claim with a shifted clock, `403 dev_disabled` on dev actions).

Friends: `GET /friends` → `{ friends: FriendSummary[] }` (accepted + incoming + outgoing, oldest first); `POST /friends/request { friendCode }` → 201 `{ userId, status: 'outgoing' | 'friend' }` (code is case-insensitive, spaces/dashes ignored; an inverse pending request is accepted directly); `POST /friends/:userId/accept` → 204 (only the addressee); `DELETE /friends/:userId` → 204 (reject, cancel or unfriend).

Weather: `GET /weather` → `WeatherResponse` `{ city, location, detected: { weather, place, via: 'location' | 'city', fetchedAt } | null, weather, source: 'detected' | 'manual' | 'none' }` (`manual` only with DEV_TOOLS=1; `place` is null for a location) — what a session started now would use (same cache and rule as `start`). For Settings and the conditions preview.

Leaderboard: `GET /leaderboard?scope=global|country|friends&period=week|month` → `LeaderboardResponse`. Only rows with points > 0. Ties share a rank (competition ranking: 1, 2, 2, 4), listed by who reached the score first. `mine` is null when the caller has no points in that period.

Privacy (`anonymousRankings`): in the `global` and `country` scopes a row of a user who turned it on has `trainerName: null` (the client shows "Anonymous trainer"), unless it is the caller's own row (`me: true`), which always carries the real name. `mine` follows the same rule, and the `friends` scope never hides names. Every row has `anonymous: boolean` (the user's setting even when the name is shown, so the caller's own row can say it is hidden). Only the name is masked: `userId`, `country`, points, league and the leader species stay in the row.

Where else a trainer name reaches another user: `GET /friends` (the name of an accepted friend, of someone who sent you a request, and of the owner of a friend code you just requested) and study groups (host and members/invitees in `StudyGroupView` and the `group` SSE event, invitations are friends-only). These are not public contexts, so they ignore `anonymousRankings`.

### Study groups ("Estudiar con amigos")

Tables `study_groups` (lobby → started / ended), `study_group_members` (one row per user who started a session in the group: `session_id`, `joined_at`, `ends_at`, `left_at`, `left_reason`) and `study_group_invites` (`pending | accepted | declined | joined | failed`). Migration `0001_study_groups`.

- `GET /groups` → `GroupsResponse { current, invites, serverNow }`: `current` = the group of my running session, else the lobby I host or accepted; `invites` = pending invites I can still answer.
- `POST /groups { minutes, friendIds (1–7 uuids) }` → 201 `StudyGroupView` (lobby, expires in 30 min). 409 `no_player`, `session_active`, `already_in_group`, `not_friends`, `cannot_invite_self`, `group_full` (8 people).
- `GET /groups/:id` → view (participants only, else 404).
- `POST /groups/:id/invite { friendIds }` (host; lobby or a started group someone is still in). Declined/failed invitees are asked again.
- `POST /groups/:id/accept`: lobby → `accepted`; started → **late join**: the server starts the caller's session now (same minutes) and records the member row. 409 `session_active`, `already_in_group`, `group_ended`, `invite_closed`, `not_friends`.
- `POST /groups/:id/decline` → 204.
- `POST /groups/:id/start` (host): host and every accepted invitee start a session at the same instant (each in a savepoint; an invitee who cannot start → `failed`, the rest go on). 409 `not_host`, `group_ended`, or the host's own start error.
- `POST /groups/:id/leave` → 204: lobby host → disband; invitee → declined; started member → out of the group, session continues solo.
- `cancel` of a long session that keeps its minutes (GDD §3.4) gets `friendOverlap` = accompanied time up to now ÷ time since joining (`claimOverlap(tx, user, doc, now)`).
- Hooks in the game action pipeline (`runGameAction`): `pause` and `cancel` (and any end of the session) close the member interval (`left_reason` `pause` / `cancel` / `finished` on claim); a solo `start` drops the user's open lobbies. **No re-joining.**
- **Claim**: `friendOverlap` = time of my in-group interval during which at least one other member was in theirs ÷ my session minutes (`src/game/group.ts`), passed to the reducer as `ActionEnv.friendOverlap` (never from the client) and stored in `SessionResult.friendOverlap`. Fairy multiplier = `1 + (fairy − 1) × friendOverlap`.
- Rate limits per user: create + invite 20 / 15 min; other group writes 120 / 15 min.

### Trades between friends (GDD §12.8)

Table `trade_offers` (migration `0012_trades`, which also adds `friendships.accepted_at`, backfilled with `created_at` for friendships accepted before it). One row per offer, open or closed; the closed rows are each player's trade history. Contract and error codes: `src/game/protocol.ts` «Trades»; rules: `src/engine/trade.ts`; config `trade.*` (`src/engine/config.ts`, not editable live).

Flow: A offers one Pokémon to B (`offered`, optional message up to 80 graphemes) → B picks one of theirs (`countered`: B's confirmation) → A accepts (`completed`) or rejects. A can `cancel` and B can `reject` any open offer; A can also reject a counteroffer. An open offer lapses 72 h after it was made or countered (`expired`, swept lazily on every trades request of either player). Unfriending cancels the open offers between the two.

- `GET /trades` → `TradesResponse { incoming, outgoing, history (last 50 closed), lockedUids, today, dailyLimit, serverNow }`. Open offers show the Pokémon as they are now in their owners' docs (`missing: true` if one is gone); closed ones the snapshot taken at completion.
- `POST /trades { toUserId, uid, message? }` → 201 `TradeOfferView`. `POST /trades/:id/counter { uid }`, `/accept`, `/reject`, `/cancel` → `TradeOfferView`.
- Rules, checked at every step and all again on completion: accepted friendship of at least `trade.minFriendshipDays` (3) days (`friendship_too_new` + `readyAt`); not a team member, a member of the running session or the last Pokémon; a legendary/mythical only once in its life (`OwnedPokemon.traded.count`); one open offer per Pokémon (also enforced by two partial unique indexes); at most 10 open offers sent; the receiver's level cap (§12.5); 3 completed trades per player and local day (`PlayerState.trades`); Dust. Errors carry `side: 'me' | 'partner'`.
- **Cost:** both players pay the same Dust, that of the dearer of the two Pokémon (100, ×5 shiny, ×10 legendary/mythical, multiplied together). Charged only on completion; not enough Dust → 409 and nothing changes, the offer stays open.
- **Completion** (`accept`): locks both `player_docs` rows `FOR UPDATE` in user-id order, then the offer row (every other route locks at most one doc, always before the offer, so there is no lock cycle); re-checks everything; the Pokémon must still have the species and shininess both players saw (`pokemon_changed`); applies both sides with `applyTrade` or none; bumps both doc versions; publishes `game` to both.
- What moves: the whole individual (level, EXP, IVs, nature, mint, Bottle Caps, ability, techniques incl. TMs, Mastery, shiny, Tera until it lapses, nickname); Bond back to 0, a pending Rest dropped, `traded { originalTrainer, receivedFrom, receivedAt, count }` recorded; Kadabra, Machoke, Graveler and Haunter evolve on arrival; the species (and its evolution) count as seen and caught; `pendingTrades` queues the arrival window (`ackTrade` empties it). No trainer EXP for a new species received by trade.
- SSE `{ type: 'trade', offerId, status, userId, trainerName }` to both players on every change; a best-effort Web Push («X te ofrece un intercambio» / counteroffer) to the player whose turn it is, when push is configured.
- Rate limits per user: new offers 20 / 15 min; other trade writes 120 / 15 min.

### Live content (public)

Design: `docs/admin-plan.md` §1. Code: `server/content/service.ts`, `server/routes/content.ts`. Operating guide for the admin: `docs/admin.md`.

- `GET /content` (public, no session) → `ContentResponse { hash, baseHash, patch, events, eventItems }`: the published version with the latest `effective_at <= now` (game time, so `x-dev-now` applies with DEV_TOOLS=1) plus the live events active now (full `EventOverlay`s, with their missions; not the page-oriented `LiveEventPublic`). `ETag: "<hash>"`, `Cache-Control: no-cache`; `If-None-Match` with the same hash → 304. Nothing published = `{ hash: 'base', patch: {}, events: [], eventItems: {} }`. The client rebuilds the context with `createEngineContext(resolveContent(patch, events, eventItems, { hash }))`; a `baseHash` different from its bundled `src/data/game/meta.json` means the client is stale.
- `GET /content/:hash` → the same body for a pinned hash (`ActiveSession.contentHash` / `EncounterState.contentHash`). `Cache-Control: public, max-age=31536000, immutable` (a hash never changes meaning), except `base` (no-cache: it moves with each deploy). 404 `unknown_content` for a hash that is not in `content_snapshots` (or malformed). Drafts and archived versions are never resolved.
- **Hash**: `'base'` when there is no patch, no active event and no event items; otherwise `sha256(baseHash + canonicalJson({ patch, events, eventItems }))` (sorted keys). The engine never hashes.
- **Pinning** (`contentForAction` in `runGameAction`): `start` runs on the current content and the reducer stores its hash on `activeSession.contentHash` (only when it is not `'base'`, so without a published patch the saved doc is byte-for-byte what it was); the same transaction writes the `content_snapshots` row (`INSERT … ON CONFLICT DO NOTHING`). `claim` and `cancel` run on the session's content; `claim` copies the hash to `encounter.contentHash`; `throwBall`, `applyStatus`, `reroll`, `assignDamage`, `autoAssignDamage`, `nextWave`, `finishWaves` run on the encounter's. Absent hash = `'base'`. Everything else (candies, evolution, missions, team…) runs on the current content. A pinned hash missing from the snapshots (should not happen) falls back to the current content with a warning. Study-group starts go through `runGameAction`, so they pin too.
- Publishing in the middle of a session does not change that session; a session started during an event keeps the event's content until its waves end, and one started before does not get it. Some changes cannot be pinned and apply at once to everyone (candies, level caps, Pokémon already caught, league thresholds of the current week): the validator reports them as `live_owned` / `live_league_week` warnings.
- **Service**: published versions and events (`server/content/events.ts`: `published` rows of `live_events`, plus `archived` ones as `retired` so their items keep their names) are kept in memory and reloaded every 60 s (lazily, on the next request) and right after a publication in this process; patches of published versions (immutable) are cached; the resolved context is memoized by `versionId + [eventId@revision]` and an LRU of 32 hashes. Writes go through `deps.content.publishDraft(tx, id, …)` / `publish(…, tx)` inside the admin route's transaction, then `refresh()` after the commit (tests also call `deps.content.publish({ patch, effectiveAt?, … })`).
- **Broadcast**: `deps.content.check()` sends `{ type: 'content', hash }` to every SSE connection (`EventBus.broadcast`) when the active hash changed since the last check. `server/index.ts` runs it every 30 s (scheduled versions, event start/end); `refresh()` runs it right after an admin write. The first check after boot only records the hash.
- After a redeploy that changes the base data, an old snapshot is rebuilt on the new base (a warning is logged): only the patch and overlays are stored, not the whole data.

**Tables** (migrations; all of them live in PostgreSQL and must be backed up with it): `0005_admin_roles_audit` (`users.role`, `auth_sessions.elevated_until`, `admin_audit`), `0006_content_versions` (`content_versions`, `content_snapshots`), `0007_session_log` (`session_log`), `0008_live_events_uploads` (`live_events`, `live_event_revisions`, `uploads`), `0009_content_sim_runs` (`content_sim_runs`), `0010_event_announce` (`live_events.announce_rev`, default 0), `0011_content_event_link` (`content_versions.linked_event_id` → `live_events` on delete set null, `linked_role` `start|end` with a check, `revert_of_version_id`, index on `linked_event_id`).

### Live events (public)

- `GET /api/live-events` (public, `Cache-Control: no-cache`; game time like `/content`) → `LiveEventsResponse { active, upcoming, past, nextCursor, serverNow }`. Only **published** events: drafts and archived events never appear, and only public fields are returned (id, slug, `name`/`description` `{es,en}`, `image {url, thumbUrl, width, height}` or null, `startsAt`/`endsAt`, `announceRev`, `featured`, `shiny`, `legendaryChanceMult`, `drops`, `missions`, `items`; no authors, no validation). `active`: `startsAt <= now < endsAt`; `upcoming`: starting within 60 days; `past`: ended within 90 days, newest first, 20 per page (`?before=<endsAt ms>`; `nextCursor` null on the last page; 400 `invalid_query` for a malformed one). The events that apply to game rules go through `GET /api/content` (hash, `events`) and the pinned session snapshots; this endpoint is for the Events page (`#/events`) and the banner. The client refetches it on the SSE `content` and `event_announce` events.
- **Event window** (client, `src/ui/screens/events/popup.ts`, `EventPopup.tsx`): a pop-up is owed per (event, `announceRev`, phase) until the device has shown it (`localStorage` `pokefocus:eventPopup:seen`, last 100 keys, try/catch). Phase `active` (running; `announceRev` 0 is the automatic first showing) or `upcoming` (only when `announceRev >= 1`, i.e. after an admin notified: «Coming soon» with the start date). It opens only at a calm moment: home phase `idle` or `results` (never focus, paused, claim, late, waves, break), no Profe Pika hint, no other dialog, «What's new?» not due; one at a time; if the player is on `#/events` it is just recorded as seen. Players who connect later get it from `GET /api/live-events` (nothing is stored per player on the server).
- **Description format** (`src/game/richText.ts`, pure, shared by server and client): `**bold**`, `*italic*`, `[red|orange|yellow|green|blue|purple|pink]…[/…]`, `\*` `\[` `\\` escapes, nesting up to 6 levels; anything unparseable is literal text. Rendered as React elements (no HTML). The description validator (`richLongTextSchema`) counts **visible** characters (max 400 per language, markers and escapes do not count) and caps the stored string at 3x that (1200), 400 `invalid_body` otherwise; a description with only markers is blank. Names and mission texts stay plain.
- Events live in `live_events` (`draft | published | archived`, `revision`, `overlay` jsonb). A session pins its content hash at start, so an event that began after the session started does not affect it.

### Web Push

**Why.** The page shows the end-of-session notification itself (the leader tab, then `markNotified` sets `timer.notified = true`). But a browser may freeze a hidden tab (Chrome Memory/Energy Saver): then nobody notifies, the player comes back after the claim window and gets the late-claim multiplier. So the server also pushes a notification through the browser's push service (FCM, Mozilla autopush, Apple, WNS) as a **fallback**. The claim window itself does not change.

**Rule** (contract in `src/game/protocol.ts`, code in `server/push.ts`). `runDue()` runs every 15 s (`server/index.ts`, only with VAPID keys) and pushes a session when all hold:

- the player has at least one row in `push_subscriptions`;
- `timer.pausedAt` is null and `timer.notified` is not true (the dedupe: a live page has already notified, so the player never gets two notices);
- `now >= timer.endsAt + PUSH_GRACE_MS` (20 s: the page gets the first chance) and `timer.endsAt > now - PUSH_MAX_AGE_MS` (30 min: no stale pushes after downtime);
- nothing was sent for `(user, sessionId)` yet. `push_sent` (PK `user_id, session_id, kind`) is claimed with `INSERT … ON CONFLICT … RETURNING` before sending, so overlapping runs and restarts send at most once.

The candidates come from one SQL query over `player_docs.doc->'timer'` with `EXISTS (push_subscriptions)` (users without subscriptions cost nothing); the doc is re-read and the rule re-checked right before claiming. Payload (`PushPayload`, JSON, localized by `player.profile.locale`, default English): `{ type: 'session-end', title, body, tag: 'pokefocus-session', url: '/' }`, body built from `claimWindowMinutes` of the game config. Sent with `TTL` = the claim window (a later push is useless) and `Urgency: high`, a 10 s deadline per subscription, all subscriptions in parallel. Push-service answers: 404/410 → the subscription is deleted; success → `last_success_at`; if **every** delivery failed transiently (network, timeout, 429, 5xx) the claim is released (`sent_at = NULL`) and the next tick retries, at most 3 attempts in total (`push_sent.attempts`). Other errors (400/401/403/413) keep the subscription and do not retry.

**Setup.** `npm run vapid` prints `VAPID_PUBLIC_KEY=…`, `VAPID_PRIVATE_KEY=…`, `VAPID_SUBJECT=mailto:you@example.com` (edit the subject); paste them into `.env` (or the compose environment). Generate the pair once: new keys invalidate every existing browser subscription. Keys and endpoints are never logged.

**Endpoints** (all need the session cookie; `POST`s need `Origin` + JSON like every other write):

- `GET /push/config` → `PushConfigResponse { enabled, publicKey }` (`Cache-Control: no-store`). Without VAPID keys: `{ enabled: false, publicKey: null }`.
- `POST /push/subscribe { endpoint, keys: { p256dh, auth } }` (the browser's `PushSubscription.toJSON()`) → 204. Upsert by endpoint: an endpoint known for another account moves to the caller (same browser, different login). At most 10 per user → 409 `too_many` (re-subscribing an own endpoint does not count).
- `POST /push/unsubscribe { endpoint }` → 204; removes only the caller's own row; idempotent.
- `POST /push/test` → 200 `{ sent }`: sends a `type: 'test'` payload to every subscription of the caller (409 `no_subscription` with none). Use it to check the whole chain on a real browser.
- Errors: 404 `push_disabled` (subscribe / unsubscribe / test without VAPID keys), 400 `invalid_body`, 409 `too_many` / `no_subscription`, 429 `rate_limited` (subscribe + unsubscribe: 30 / 15 min per user; test: 5 / h per user).

**SSRF guard.** The server only POSTs to real push services. An endpoint must be an `https:` URL of at most 2048 characters, without credentials, on port 443, and its host must equal or end in `.` + one of: `googleapis.com` (FCM: `fcm.googleapis.com`), `push.services.mozilla.com` (`updates.push.services.mozilla.com`), `push.apple.com` (`web.push.apple.com`), `notify.windows.com` (`*.notify.windows.com`). So `fcm.googleapis.com.evil.com` and `evilgoogleapis.com` are rejected. `p256dh` must decode (base64url) to a 65-byte uncompressed P-256 point and `auth` to 16 bytes.

**Single instance.** The scheduler runs in the process (no overlapping runs in one process). Two instances on one database would still send at most once (`push_sent`), but like the event bus and the rate limiter this assumes one server.

**Service worker.** In production `/sw.js` (from `public/sw.js`, copied to `dist/` by Vite) is served with `Content-Type: text/javascript` and `Cache-Control: no-cache`, and a missing `/sw.js` is a 404, never the SPA `index.html`.

Testing locally: set the three `VAPID_*` in `.env`, enable notifications in Settings, then `POST /api/push/test` (or the Settings button). For the fallback, start a short session, close or freeze the tab (`chrome://discards`) and wait for `endsAt` + 20 s. Push services need a reachable https origin or `localhost`.

### Server-Sent Events

`GET /api/events` (use `new EventSource('/api/events')`; same-origin, the cookie goes along). Each event is an unnamed message (`onmessage`) whose `data` is a JSON `ServerEvent`:

- `{ type: 'game', version }` after every successful write of the user's doc (from any tab, including the one that made it — compare `version` and ignore what you already have).
- `{ type: 'friends' }` to both users on request / accept / remove.
- `{ type: 'group', groupId, kind, userId, trainerName, reason? }` to every participant of a study group on invite / accept / decline / start / join / leave / disband / failed (`kind`); `reason` on `leave` (`pause | cancel | leave | finished`). Refetch `GET /api/groups`.
- `{ type: 'content', hash }` to **every** connection when the active live content changes (publication, scheduled version, an event starting or ending, publishing/archiving/editing an event: the 30 s tick compares the hash and `GET /api/live-events` follows it). Refetch `GET /api/content`; screens of a pinned session keep their hash.
- `{ type: 'event_announce', eventId, rev }` to **every** connection when an admin presses «Notify players» on a published event (`POST /api/admin/events/:id/announce`). The client refetches `GET /api/live-events` and shows the event window again for `rev` (see *Live events (public)*).
- `{ type: 'trade', offerId, status, userId, trainerName }` to both players of a trade offer on every change (offered, countered, completed, rejected, cancelled, expired). Refetch `GET /api/trades`.
- `{ type: 'logout' }` to the connections of a revoked session (logout-all, password change, DELETE /auth/sessions/:id), then the stream closes.

The stream starts with `retry: 5000` and sends a `: ping` comment every 25 s. 401 if there is no session.

### Roles and access

Migration `0005_admin_roles_audit`: `users.role` (`player` default | `support` | `admin`, check constraint), `auth_sessions.elevated_until` and the `admin_audit` table. `PublicUser.role` is returned by `/auth/*`; the server re-reads the role from the database on every request, so a demotion applies at once. The admin screen is `#/admin` (reached by URL, not in the menu; tabs Content, Events, Players, Metrics, Maintenance; the server is the authority on what each role may do). It uses the signed-in session; without a staff role only the Maintenance tab is offered, with a field for the deprecated token.

- **Guards** (`server/http.ts`): `requireRole('support'|'admin')` after `requireAuth` (403 `forbidden`; order player < support < admin) and `requireElevated(deps)` for sensitive actions (403 `elevation_required` unless the session's `elevated_until` is in the future).
- `GET /admin/me` (support+) → `{ role, elevated, elevatedUntil, serverNow }`.
- `POST /admin/reauth { password }` (support+): verifies the password like the login does (with the pepper) and sets `elevated_until = now + 30 min` **on the current session only** («sudo mode»); answers like `/me`. Wrong password: 403 `wrong_password`. Limit 5 wrong guesses / 15 min per user (cleared by a right one). Audited as `admin.reauth`.
- **Rate limit**: every admin request of a signed-in user counts against `adminUser` (600 / 15 min per user, 429 `rate_limited`); the specific limits are listed with each area below.
- **Audit** (`server/admin/audit.ts`): `audit(tx, c, { action, targetType, targetId, before, after, note })` inserts into `admin_audit` (`actor_id` or `actor_label`, `ip`, `created_at`) using the caller's transaction, so the change and its record commit or roll back together. Actors: the user (`actor_id`), `token` (legacy token), `system` (start-up promotion), `cli`. Actions: `admin.reauth`, `user.role`, `maintenance.create|delete`, `player.grant|unlock|cancel_session|logout_all`, `content.draft.create|update|delete`, `content.simulate`, `content.publish|schedule|reschedule|unschedule|rollback`, `event.create|update|delete|publish|archive|announce`, `upload.create|delete`. (Draft validation is derived data and is not audited.)
- **Becoming admin** (accounts are created by normal registration; roles are never self-service):
  - `ADMIN_EMAILS=you@example.com` + restart: existing accounts with those emails become `admin` (idempotent; never demotes; audited as `user.role` by `system`). Emails without an account are skipped with a warning: **register first, then restart** (the email is not verified, so never list one that nobody trusted owns).
  - CLI: `npm run admin:role -- you@example.com admin` (roles `player|support|admin`; reads `.env`; audited as `cli`). With the embedded PGlite the directory cannot be shared with a running server: stop it first (PostgreSQL has no such limit).

### Metrics

`GET /admin/metrics?from&to&granularity` (support+; `from`/`to` epoch ms, default the last 28 days; `granularity` `day` (default) | `week`) → `AdminMetricsResponse { from, to, granularity, serverNow, buckets, totals }`. Buckets are whole **UTC** days or weeks (Monday start; the range is widened to whole buckets), at most 120 (400 `range_too_large`; 400 `invalid_body` for malformed or reversed parameters). Each bucket: `activePlayers`, `sessions`, `minutes`, `points`, `wilds`, `catches`, `shinies`, `legendaries`, the Focus bands `focusLow` (< 0.75) / `focusMid` (0.75 to < 1) / `focusFull` (≥ 1), and a simple retention (`prevActive` = players active in the previous bucket, `returned` = those who came back). `totals.activePlayers` counts distinct players over the whole range. No player ids or names leave the server.

Source: `session_log` (migration `0007_session_log`; `server/session-log.ts`), one row per **claimed valid session** (and per cancelled long session that keeps its minutes, GDD §3.4), written inside the action's transaction so it commits with the player document; unique per `(user, session)`, with the content hash the session ran with. Later ball throws update the row's `catches`. History starts when the migration was applied (nothing is backfilled).

### Maintenance (admin side)

For a signed-in user with role `admin` (session cookie) **or** the deprecated `Authorization: Bearer <ADMIN_TOKEN>`:

- `GET /admin/maintenance` → `{ items, serverNow }`: the same windows as the public list plus `createdAt`.
- `POST /admin/maintenance { startsAt, endsAt, note? }` → 201 `{ item }`. `startsAt`/`endsAt` are integer epoch ms with `endsAt > startsAt`, `endsAt` in the future and a window of at most 14 days; `note` is trimmed (empty = none) and at most 280 characters. Otherwise 400 `invalid_body` (+ `fields`). At most 20 windows that have not ended: 409 `too_many`.
- `DELETE /admin/maintenance/:id` → 204 (404 `not_found` for an unknown or malformed id).
- Who may call it: with an `Authorization` header the request is a token request; without one, a session cookie is resolved and the user must be `admin` (403 `forbidden` otherwise). Creating and deleting are written to `admin_audit` (`maintenance.create` / `maintenance.delete`).
- **Deprecated token** (removed in the next version). Checks run in this order: `ADMIN_TOKEN` unset → 404 `admin_disabled`; rate limit → 429 `rate_limited`; token → 401 `unauthorized`. The token is compared in constant time (sha256 of both sides + `timingSafeEqual`). Limit: 10 requests / 15 min per client IP (set `TRUST_PROXY=1` behind a proxy), counted on every request and cleared by a valid token, so a legitimate admin is never locked out. The token opens **only** this route; it never touches player data.

```bash
H=(-H "Authorization: Bearer $ADMIN_TOKEN" -H "Origin: https://pokefocus.example" -H "Content-Type: application/json")
# Schedule: Friday 2026-11-13 02:00-03:00 UTC
curl "${H[@]}" -X POST https://pokefocus.example/api/admin/maintenance \
  -d "{\"startsAt\": $(date -u -d '2026-11-13 02:00' +%s)000, \"endsAt\": $(date -u -d '2026-11-13 03:00' +%s)000, \"note\": \"Database upgrade\"}"
curl "${H[@]}" https://pokefocus.example/api/admin/maintenance            # list (ids)
curl "${H[@]}" -X DELETE https://pokefocus.example/api/admin/maintenance/<id>   # cancel
```

### Player support

`server/routes/admin/players.ts`, `src/game/admin.ts`. Every mutation is audited in the same transaction and counts against `adminPlayerWrite` (60 / 15 min per staff user); grants also against `adminGrant` (20 / 15 min).

- `GET /admin/players?q=` (support+; 2..60 chars over email, trainer name, friend code; at most 20; 400 `invalid_query`) and `GET /admin/players/:id` (profile, 30-day locks, doc summary, last 20 sessions, signed-in browsers).
- `POST /admin/players/:id/unlock {field: trainerName|country|timezone, reason?}` (409 `not_locked` when there is no lock), `/cancel-session {reason?}` (the same reducer and mirrors as the player's own `cancel`, so a session already past `endsAt` is refused, 409 `already_finished`, and a long one keeps its minutes by the normal rules), `/logout-all {reason?}` (not on yourself: 409 `self_target`): support+, but support only on `player` accounts (403 `forbidden_target` otherwise).
- `POST /admin/players/:id/grant {items?, dust?, reason}`: **admin + sudo**. Positive integers only; at most 10 item kinds, 50 units each and 5000 Dust per request (400 `empty_grant`, `too_many_items`, `unknown_item`, `invalid_amount`, `amount_too_large`); the reason (5..280 characters) is the audit note. 409 `no_player` when the account has not created a trainer. `applyAdminGrant` is not a `GameAction`: clients cannot send it. The player gets the usual `game` SSE event.

### Live content admin

`server/routes/admin/content.ts`, mounted at `/api/admin/content`; pure helpers `diffPatches` / `spawnPreview` in `src/game/content/`. Only `published` versions reach `/api/content`: drafts never do.

- Reads (support+): `GET /live` (hash in force, active version, next scheduled one, active events), `GET /versions?status=draft|published|archived` (newest first, at most 100, with author, dates, `active`, `scheduled` and validation counts), `GET /versions/:id` (patch, full last validation and the `diff` against the active patch: `{path, kind: added|changed|removed, before, after}`; drafts also carry `sim`).
- Drafts (admin): `POST /drafts {from?: 'active'(default)|'empty', fromVersionId?, title?, note?}` → 201 (at most 20 open drafts: 409 `too_many_drafts`); `PUT /drafts/:id {patch?, title?, note?}` saves **even with errors** and stores the cheap validation (no smoke test) so a work in progress is never lost; `DELETE /drafts/:id` → 204; `POST /drafts/:id/validate` runs the full validation (shape + references + spawn coverage + big-change guard + engine smoke test, ~0.3 s) against the content in force (previous patch, active events) and stores it. Anything on a non-draft: 409 `not_draft`. A patch is a **full patch over the base**, not a delta over the previous version.
- **Publish / schedule** (admin + sudo): `POST /drafts/:id/publish {effectiveAt?, linkEventId?, revertWhenEnds?, confirm?, note?}` (`linkEventId` / `revertWhenEnds`: see «Content tied to an event» below; `effectiveAt` and `linkEventId` together are 400 `invalid_body`). No `effectiveAt` = now; a future one (at most 60 days ahead, otherwise 400 `invalid_effective_at`) schedules it (audited as `content.schedule`). It validates again with the smoke test inside the transaction: errors block with 422 `validation_failed {errors, warnings, requiresConfirm}`; warnings that need confirmation (a number moved by more than ×3 from the base, a probability by more than ×5) need `confirm: true` (409 `confirm_required {warnings}`). The reference of that guard is **the patch in force now** (`previous` = `active.patch`: what really changes when this version is published), not the base: a draft created from live does not ask again for values that are already live and that it leaves alone, while a value moved further, or one dropped back to the base, does. Each warning carries `params {base, value, factor, kind, from: 'live'|'base'}` (`base` is the reference value, `kind` the limit kind so the UI formats it like the table: probabilities as %; `from` is `base` while nothing is published). `GET /live` returns the patch in force (`patch`) so the editor's live check uses the same reference. The row becomes `published` (immutable) through `ContentService.publishDraft` in the route's transaction; after the commit `ContentService.refresh()` reloads and broadcasts `{type:'content', hash}` if the active hash changed.
- **Rollback** (admin + sudo): `POST /versions/:id/rollback {confirm?, note?}` → 201: a NEW published version with the old patch (`parent_id` = the restored version, titled `Rollback to #<id>`, effective now). Only a version that already took effect can be restored (409 `not_published` for drafts and scheduled-for-later ones). It is validated like a publication. A version scheduled for later still overrides it when its time comes (cancel it first with `unschedule` if that is not wanted).
- **Unschedule** (admin + sudo): `POST /versions/:id/unschedule` → 200 `AdminContentVersionResponse`: a *scheduled* version (published, `effectiveAt` in the future) goes back to a `draft` (`effectiveAt`, `publishedBy` and `publishedAt` cleared; same patch and hash), so it can be edited, deleted or scheduled again. 409 `not_scheduled` for drafts and for versions already in force (those are immutable: roll back instead), 409 `too_many_drafts` when 20 drafts are already open. Audited as `content.unschedule` in the same transaction; afterwards `ContentService.refresh()` reloads the schedule and announces the hash over SSE only if the active hash changed (it normally does not: the cancelled version was not in force). Rate limit: the publish/rollback bucket.
- `GET /spawn-preview?versionId&eventId&hour(0-23, 12)&weather(rain|sun|snow|clear|unknown, clear)&trainerLevel(1-100, 1)` (admin): the non-legendary species the wild pool offers for that slot under a draft/version (default: the active content), with `probability` (average over the wild levels of the band, neutral first wave: weight = captureRate x spawn rule), plus the spawn `rules` in force. `eventId` (any status, drafts too) previews with that live event on top. It reuses `spawnRuleMult` of the coverage check. 422 `invalid_patch` when a stored patch does not resolve.
- **Content tied to an event** (`server/content/eventLink.ts`; columns of `0011`). Version summaries (`/live`, `/versions`, `/versions/:id`, the publish result) carry `linkedEvent {id, slug, name, status, startsAt, endsAt}`, `linkedRole` (`start|end`), `revertOfVersionId` and `revertStale`.
  - *Publish tied*: `linkEventId` = a `published` event with `endsAt > now` (422 `unknown_event`; 409 `event_not_linkable {reason: 'not_published'|'ended'}`; the event row is locked `FOR UPDATE` before the draft, the same order the events routes use). `effectiveAt = max(event.startsAt, now)`: a running event means in force now; otherwise it is `scheduled` at the event's start (no 60-day check: publishing the event already applied it). Validation, `confirm` (×3 / ×5), sudo and rate limit are those of a normal publish. The row gets `linked_event_id` and `linked_role = 'start'`. Audit: `content.schedule` (always, also when it enters now) with `after {linkedEventId, eventSlug, linkedRole, eventStartsAt, eventEndsAt, immediate, revertWhenEnds, …}`.
  - *`revertWhenEnds`*: in the same transaction a second version is inserted through `ContentService.publish(…, tx)`: `status published`, `effective_at = event.endsAt`, `linked_role = 'end'`, `revert_of_version_id` = the start version, title `Back after <slug>`, `parent_id` = the version it copies, patch = the latest published version with `effectiveAt <= max(startsAt, now)` **that is not tied to this event**, or `{}` (the base) when there is none; so a version scheduled for before the event counts, one scheduled during it does not. Not validated again (it is a copy of a previously valid state). The publish response carries it as `revert` (`AdminContentVersionSummary`); it has its own `content.schedule` audit row (`after {linkedRole: 'end', revertOfVersionId, copiedFromVersionId}`). An empty patch resolves to the base content (`hash: 'base'`, no active version id), which is what «back to nothing» means.
  - *Follows the event* (events routes, same transaction as the event write): `PUT /events/:id` on a published event whose `startsAt` or `endsAt` changed moves the **scheduled** (`effectiveAt > now`) versions tied to it: `start` → `max(newStart, now)`, `end` → `newEnd`; each move is audited as `content.reschedule` (`before/after {effectiveAt}`, `eventId`, `role`) and the response lists the ids in `contentMoved`. `POST /events/:id/archive` on an event whose `startsAt > now` sends every scheduled version tied to it (both roles) back to `draft` with the link cleared (`toDraft`, audited as `content.unschedule` with note `event archived before it started`; the 20-draft cap is not applied here) and lists them in `contentCancelled`. Once the event started nothing is touched: the start version is in force (immutable) and a scheduled `end` copy still fires at the planned `endsAt`. Versions already in force are never moved.
  - *Unschedule by hand*: `POST /versions/:id/unschedule` on a tied version also clears the link (`linked_event_id`, `linked_role`, `revert_of_version_id` → null: a draft is never tied); when it is a `start` version its scheduled `end` copies (`revert_of_version_id = id`) go back to drafts in the same transaction.
  - *Out-of-date copies*: nothing cancels or recomputes an `end` version when another version is published by hand. `revertStale` (computed on read for scheduled `end` versions, `staleReverts`) is true when a published version **not tied to that event** takes effect in `(start version's effectiveAt, end effectiveAt]`, or when the latest published version at that start (excluding the event's own) no longer has the copy's hash. The copy still fires and overrides whatever came in between.
  - `GET /api/admin/events/:id` (single event only, not the list) adds `linkedContent: [{id, title, role, effectiveAt, active, scheduled, revertStale}]` (published versions tied to it, oldest first). `PUT` adds `contentMoved?: number[]`, archive `contentCancelled?: number[]`. Deleting an event row sets `linked_event_id` to null (only drafts can be deleted, and drafts cannot be linked).
- Limits per staff user (429 `rate_limited`): draft writes 120 / 15 min; validate + spawn preview + simulate 30 / 15 min; publish + rollback + unschedule 10 / 15 min. Request bodies under `/api/admin/content` and `/api/admin/events` may be up to 512 KB (64 KB elsewhere). Audit rows hold hashes and counts of changed paths, not whole patches.

#### Simulation

Migration `0009_content_sim_runs`; contract in `protocol.ts` «Admin: balance simulation»; code `server/content/simCompare.ts`, `simWorker.ts`, `simRunner.ts`.

- `POST /content/drafts/:id/simulate {profiles?, seeds?, weeks?}` (admin) → 202 `{run}`: the simulator of `scripts/sim` (`runMatrix`, missions on, damage policy `auto`) plays the same profiles and seeds on the **active patch** and on the **draft's patch** (live events are left out: they are dated and temporary) in a `worker_threads` worker, and stores the comparison per profile: weekly points (quartiles per week and the median), league reach, sessions, minutes/day, captures, species caught, legendaries and shinies seen/caught, dust earned/spent/final, Energy (exhausted share, started empty, energy left) and rests.
- Profiles: `casual`, `constant`, `marathoner`, `night-owl`, `irregular`, `grinder` (default the first three), seeds 1-20 (default 4), weeks 1-8 (default 4). Profiles x seeds x weeks <= 480 (400 `sim_too_big`; about 60 ms per simulated player-week on a laptop, x2 for both sides). One run at a time per server (409 `busy`), cancelled after 5 min (`timeout`), worker heap 512 MB. The draft must have no validation errors (cheap validation: 422 `validation_failed`); 409 `not_draft`. Audited as `content.simulate` (params and hashes).
- `GET /content/sim-runs?versionId=` (support+; newest first, at most 50, no reports, `busy`) and `GET /content/sim-runs/:id` (support+; `progress {done, total}` while running, `report` when done). Rows: `running` → `done` | `failed` | `timeout`; a row still `running` after a restart becomes `interrupted` (checked on the next read).
- **«Mandatory» simulation = a warning, not a block**: `GET /versions/:id` of a draft and the publish response carry `sim: {recent, last}`; `recent` = a `done` run of the draft's current patch hash (`draft_hash`) in the last 7 days (editing the patch makes it stale). Publishing without one is allowed; the `content.publish|schedule` audit row records `simRunId` (null = published unsimulated).
- Production: the image copies `scripts/sim` (Dockerfile) and `tsx` is a runtime dependency, so the worker runs from sources like the server.

### Live events admin

`server/routes/admin/events.ts`, mounted at `/api/admin/events`; contract in `protocol.ts` «Live events». All routes are **admin**; the overlay (featured species, shiny, legendary multiplier, drops, event missions, own items) is checked by `validateEventOverlay` (`src/game/content`). The `live_events` row id is the event id (`EventOverlay.id`); `slug` is unique across statuses. An event lasts at most 62 days (a validation error otherwise); name 1-80 characters and description 1-400 *visible* characters (rich format, see *Description format*) per language.

- `GET /events?status=` (newest first, at most 200), `GET /events/:id`, `POST /events {slug, name{es,en}, description{es,en}, startsAt, endsAt, imageId?, overlay}` → 201 draft (at most 50 open drafts: 409 `too_many_drafts`; 409 `slug_taken`; 422 `unknown_image`; 400 `invalid_body {fields}` for a malformed body; 400 `invalid_dates {reason: 'order'}` when `endsAt <= startsAt`), `PUT /events/:id` (partial; `confirm?`), `DELETE /events/:id` → 204 (**drafts only**, 409 `not_draft`).
- A **draft** is saved even with semantic errors (unknown species…): the cheap validation (no smoke test) is stored in `validation`. A **published** event can still be edited but needs sudo, runs the full validation with the smoke test (422 `validation_failed`, 409 `confirm_required`), cannot change its slug (409 `slug_locked`), keeps the date rules of publishing (400 `invalid_dates {reason: 'ended'}` if the new `endsAt` is not in the future, `{reason: 'too_far'}` if `startsAt` is more than 60 days ahead; an event already running with `startsAt` in the past stays editable, and so does one that is already over as long as its dates are not touched), only asks `confirm` for the big values the edit changes (the stored overlay is the reference: weight/legendary/shiny already confirmed at publication are not asked again), bumps `revision` and takes effect at once through the ContentService (new content hash; sessions already started keep theirs). Archived events: 409 `not_editable`.
- `PUT /events/:id` on a published event with new dates, and `POST /events/:id/archive` before the start, also move / cancel the content versions tied to the event (see «Content tied to an event» under the content routes).
- `POST /events/:id/publish {confirm?, note?}` and `POST /events/:id/archive {note?}`: **admin + sudo**. Publishing needs a draft (409 `not_draft`), an `endsAt` in the future and a `startsAt` at most 60 days ahead (400 `invalid_dates {reason: 'ended'|'too_far'}`); a future `startsAt` simply means *scheduled*. Archiving needs a published event (409 `not_published`): it leaves play and the public API, but its own items keep their names in players' inventories.
- `POST /events/:id/announce {note?}` («Notify players»): **admin + sudo**. Only a **published** event that has **not ended** (409 `not_published`, 409 `event_ended`); active or scheduled both work. In one transaction it locks the row, does `announce_rev = announce_rev + 1` (no `revision` bump, no content change) and writes the audit row `event.announce` (before/after `announceRev`, `note`); after the commit it broadcasts SSE `{ type: 'event_announce', eventId, rev }` to every connection. Answer: `AdminEventAnnounceResponse` = `{ event, serverNow, notified: { connections, players } }` (what `EventBus.audience()` counted when it was sent; in-memory, this process only). Rate limit: **5 per hour per event** (429 `rate_limited`). `GET /events/:id/audience` (admin) → `{ connections, players }` for the admin's confirmation dialog.
- `live_event_revisions` keeps a snapshot at publication and at every published edit (`revision` 1, 2…). Audit actions `event.create|update|delete|publish|archive|announce` (before/after hold the full event snapshot; `announce` holds `announceRev`). Limits per staff user: writes 120 / 15 min; publish, archive and edits of a published event 20 / 15 min.

### Uploading event images

`server/routes/admin/uploads.ts`, `server/uploads.ts`. `POST /api/admin/uploads` (admin) takes the **raw image as the body** with `Content-Type: image/png|image/jpeg|image/webp`, at most 3 MB (413), and answers `201 {upload, reused: false}` (`200 {reused: true}` when the same picture is already stored; the files are written again, which heals a wiped volume). It is the only non-JSON route: `app.ts` skips the JSON content-type check for exactly `POST /api/admin/uploads` and still requires the `Origin` (no multipart is parsed: a cross-site form cannot send a raw `image/*` body). An empty body is 400 `empty_body`.

- Nothing uploaded is stored or served as is. The type must agree with the magic numbers (SVG, GIF, HEIC, HTML: 415 `unsupported_type`). sharp decodes with `limitInputPixels` 40 MP and encodes again: centred 16:9 crop, 1600x900 at most (never enlarged), 320x180 at least (422 `image_too_small`), animated images refused (422 `animated_image`), corrupt ones 422 `invalid_image`, bombs 422 `image_too_large`; webp quality 82, EXIF/ICC/XMP dropped, plus a 480 px card version. The file name is the sha256 of the result (never the original name): `UPLOADS_DIR/events/<sha>.webp` and `<sha>-480.webp`.
- `GET /api/admin/uploads` (newest first, at most 200, `inUse` = events that reference it, `totalBytes` / `limitBytes`: 500 MB total, 409 `uploads_full` past it); `DELETE /api/admin/uploads/:id` → 204 only when no event (draft, published or archived) references it (409 `in_use`) and removes the files. Limit: 20 uploads + deletes / 15 min per staff user. Audit: `upload.create|delete`.

## Security

- **Passwords**: `crypto.scrypt` N=2^15, r=8, p=1, 64-byte key, 16-byte random salt, compared with `timingSafeEqual` (maxmem raised to 64 MiB because N·r·128 = 32 MiB hits Node's default). 8–128 chars, NFKC-normalized. Never logged. With `PASSWORD_PEPPER` the scrypt input is `HMAC-SHA256(pepper, password)` and the hash is stored as `scryptp$<pepperId>$N$r$p$salt_b64$hash_b64` (`pepperId` = 8 hex chars of a sha256 of the pepper, only to pick the right one while rotating). Without a pepper (development, or accounts created before it existed) the format is `scrypt$N$r$p$salt_b64$hash_b64`; those hashes still verify and are re-hashed with the current pepper on the next successful login (`needsRehash`, conditional update so a concurrent password change is never overwritten). A hash whose pepper the server does not know never verifies and logs one warning.
- **No account enumeration on login**: unknown emails are verified against a random dummy hash, same error `invalid_credentials`. (Registration does say `email_taken`; it is rate-limited.)
- **Sessions**: 32 random bytes (base64url) in the cookie, only `sha256(token)` in `auth_sessions`. New token on every login/registration. Cookie `pf_session`: `HttpOnly; SameSite=Lax; Path=/; Max-Age=30d`, `Secure` in production. Sliding expiry: a request more than 24 h after `last_seen_at` pushes `expires_at` to now + 30 d and re-sends the cookie. Expired rows are deleted hourly.
- **CSRF**: `Origin` must be in `APP_ORIGIN` for every non-GET/HEAD request, JSON content type required, plus `SameSite=Lax`.
- **Brute force**: in-memory fixed windows — login 10 / 15 min per IP and 5 / 15 min per email (attempts; a successful login clears the email counter), register 5 / h per IP, admin API with the legacy token 10 / 15 min per IP (a valid token clears it) and 600 / 15 min per signed-in staff user. Single process only; behind a proxy set `TRUST_PROXY=1`.
- **Web Push**: endpoints restricted to known push-service hosts (https, port 443, no credentials, ≤ 2048 chars); VAPID private key only in the environment; keys and endpoints never logged.
- **Admin API**: see *Admin API*. Staff are accounts with role `support`/`admin` (session cookie, CSRF Origin check, per-user rate limit, sudo mode via password re-entry for sensitive actions, every mutation audited in its own transaction). The deprecated `ADMIN_TOKEN` (≥ 24 chars) only opens maintenance notices, compared with `timingSafeEqual` over sha256 digests; it never touches player data.
- **Authority**: time, rolls, points and captures are decided by the server. `x-dev-now` / `x-dev-seed` and `dev*` actions only with `DEV_TOOLS=1`, never in production.
- **Concurrency**: every action runs in one transaction: `SELECT … FOR UPDATE` on `player_docs` → `applyAction` → `active_study_sessions` / `league_scores` updates → `version + 1`. Two tabs never overwrite each other.
- **Event images**: see *Uploading event images*. Re-encoded (never served as uploaded), hash names, `nosniff` + `default-src 'none'`, 3 MB / 40 MP limits, admin only, audited; the upload route is the one CSRF exception (raw `image/*` body, Origin still checked).
- **Headers**: Hono `secureHeaders()` (HSTS, nosniff, frame options, COOP/CORP, no referrer…). Body limit 64 KB (512 KB under `/api/admin/content` and `/api/admin/events`, 3 MB for the image upload). All SQL through Drizzle (parameterized).

## HTTPS in production

Cookies are `Secure` in production, so the site must be served over HTTPS (browsers do accept Secure cookies on `http://localhost` for local tests). Put a reverse proxy in front of the app; with [Caddy](https://caddyserver.com) (automatic Let's Encrypt certificates):

```caddyfile
pokefocus.example.com {
	encode zstd gzip
	reverse_proxy localhost:8787 {
		# SSE: send events right away
		flush_interval -1
	}
}
```

Then run the app with `APP_ORIGIN=https://pokefocus.example.com` and `TRUST_PROXY=1` (and do not publish port 8787 to the internet: `docker-compose.yml` binds it to `127.0.0.1` by default (`APP_BIND`, `APP_PORT`); keep it that way or put Caddy in the same compose network). Serve `/media/*` through the same proxy: the images are fetched from the app's origin.
