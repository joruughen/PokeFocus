# PokeFocus server (F2)

Node + Hono API that owns every player's game state. The browser only sends intents (`POST /api/game/action`); the server runs the rules with the same engine (`src/engine`) through the pure reducer `src/game/actions.ts`, stores the result in PostgreSQL (PGlite in development) and returns the new document. Spec: `docs/F2-plan.md`. Contract: `src/game/protocol.ts`.

## Layout

```
server/
  index.ts            entry: env → database (+ migrations) → app → listen; session cleanup every hour; Web Push scheduler every 15 s
  app.ts              createApp({ env, db, bus?, limiter?, clock?, fetch?, weather?, push?, pushSender? }) — no I/O, used by tests via app.request()
  env.ts              zod-validated environment
  http.ts             ApiError, body parsing, client IP, cookie helpers, requireAuth middleware
  validation.ts       zod schemas (auth bodies, GameAction discriminated union)
  events.ts           in-memory pub/sub for SSE (keyed by user id)
  rate-limit.ts       in-memory fixed-window limiter
  auth/password.ts    scrypt hashing
  auth/tokens.ts      session tokens, friend codes
  routes/auth.ts      /api/auth/*
  routes/game.ts      /api/game, /api/game/action
  routes/social.ts    /api/friends/*, /api/leaderboard
  routes/events.ts    /api/events (SSE)
  routes/groups.ts    /api/groups (study groups)
  groups.ts           study-group helpers (membership hooks, overlap at claim, views, events)
  routes/weather.ts   /api/weather
  routes/announcements.ts  /api/announcements (public: scheduled maintenance windows)
  routes/admin.ts     /api/admin/me, /reauth, /maintenance (roles; legacy ADMIN_TOKEN for maintenance)
  admin/audit.ts      audit(tx, c, entry): admin_audit row in the caller's transaction
  admin/roles.ts      setRoleByEmail, promoteAdminEmails (ADMIN_EMAILS, CLI)
  routes/push.ts      /api/push/* (Web Push subscriptions, test push)
  push.ts             Web Push service: subscription guard, sending (web-push), runDue() scheduler body
  weather.ts          Open-Meteo client: by rounded location cell (no geocoding) or by city (geocoding); 30-min cache per cell/city, 2 s deadline
  db/schema.ts        Drizzle schema
  db/client.ts        PGlite or postgres-js + migrator
  db/migrations/      generated by drizzle-kit (npm run db:generate)
src/game/actions.ts   applyAction(doc, action, env) — pure reducer (server only)
scripts/generate-vapid.ts   npm run vapid: prints a fresh VAPID key pair as .env lines
scripts/admin-role.ts       npm run admin:role -- <email> <role>: set an account's role
```

## Running

```bash
npm run dev            # Vite on 5173 + API on 8787 (tsx watch, DEV_TOOLS=1, PGlite in .data/pglite)
npm run dev:server     # API only
npm run dev:client     # Vite only (proxies /api → http://localhost:8787)
npm test               # unit + integration tests (in-memory PGlite)
npm run typecheck      # app, node scripts and server tsconfigs
npm run build          # tsc -b (incl. server) + vite build → dist/
npm start              # production: NODE_ENV=production, serves dist/ and /api from one origin
npm run db:generate    # new migration after editing server/db/schema.ts
npm run vapid          # print a fresh VAPID key pair for Web Push (writes nothing)
docker compose up --build   # PostgreSQL 17 + app on :8787
```

Migrations are applied automatically on startup (`drizzle-orm/*/migrator`), for both drivers. To start over in development, stop the server and delete `.data/`.

## Environment

Loaded from the process environment; `server/index.ts` also reads `.env` if present (see `.env.example`).

| Variable | Default | Meaning |
|---|---|---|
| `NODE_ENV` | `development` | `production` turns on `Secure` cookies, static serving of `dist/`, and forces `DEV_TOOLS=0`. |
| `PORT` | `8787` | HTTP port. |
| `DATABASE_URL` | — | `postgres://…`. When set, PostgreSQL via postgres-js; otherwise embedded PGlite. |
| `PGLITE_DIR` | `.data/pglite` | PGlite directory (`memory://` = in memory). Ignored with `DATABASE_URL`. |
| `APP_ORIGIN` | `http://localhost:5173` | Allowed `Origin`s for non-GET requests, comma-separated. In production: the public URL. |
| `DEV_TOOLS` | `0` | `1` = accept `x-dev-now` / `x-dev-seed` and `dev*` actions. Always `0` in production. |
| `TRUST_PROXY` | `0` | `1` behind a reverse proxy: client IP = last `X-Forwarded-For` hop (rate limits). |
| `STATIC_DIR` | `dist` | Built client served in production (SPA fallback to `index.html`). |
| `ADMIN_TOKEN` | — | **Deprecated** (removed in the next version): Bearer token that still opens `/api/admin/maintenance` (audited as `actor_label: 'token'`). Unset or empty = token off (404 `admin_disabled` for token-less maintenance requests). When set it must be at least 24 characters (`openssl rand -hex 24`), otherwise the server refuses to start. Never logged. Prefer an account with role `admin`. |
| `ADMIN_EMAILS` | — | Comma-separated emails promoted to role `admin` at start-up (see *Roles and admin access*). Case-insensitive; a malformed list refuses to start. |
| `VAPID_PUBLIC_KEY` | — | Web Push public key (base64url, uncompressed P-256 point, 65 bytes). From `npm run vapid`. |
| `VAPID_PRIVATE_KEY` | — | Web Push private key (base64url, 32 bytes). Secret; never logged nor echoed in errors. |
| `VAPID_SUBJECT` | — | Contact for the push services: `mailto:you@example.com` or `https://…`. The three `VAPID_*` go together: all set = push on, none = push off (`/api/push/config` → `enabled: false`), anything else (or a malformed key) and the server refuses to start. |

## API notes for the client

All endpoints are under `/api`, JSON in and out, cookie `pf_session`. Errors are `{ error: code }` (sometimes with extra fields).

**Every non-GET request** must send `Origin` (browsers do) from `APP_ORIGIN` and `Content-Type: application/json` — also bodyless ones (`logout`, `DELETE …`, `accept`). Otherwise `403 bad_origin` / `415 json_required`.

| Status | Codes |
|---|---|
| 400 | `invalid_json`, `invalid_body` (+ `fields: string[]`), `invalid_scope`, `invalid_period` |
| 401 | `unauthorized` (no/expired/revoked session, or a wrong admin token), `invalid_credentials` (login: wrong password **or** unknown email) |
| 403 | `bad_origin`, `dev_disabled` (dev action without DEV_TOOLS), `wrong_password` (POST /auth/password) |
| 404 | `not_found`, `unknown_friend_code`, `admin_disabled` (no `ADMIN_TOKEN` on the server) |
| 409 | game rule errors (see below), `email_taken`, `cannot_add_self`, `already_friends`, `already_requested`, `too_many_friends`, `too_many` (maintenance windows), `name_locked` / `country_locked` (PATCH /auth/me, with `unlockAt`) |
| 413 | `body_too_large` (> 64 KB) |
| 415 | `json_required` |
| 429 | `rate_limited` (+ `retryAfter` seconds; also the `Retry-After` header) |

Auth: `POST /auth/register` → 201 `{ user }`; `POST /auth/login` → `{ user }`; `POST /auth/logout` (no session needed) → 204; `POST /auth/logout-all` → 204; `GET/PATCH /auth/me`; `POST /auth/password { current, next }` → 204 (other sessions revoked, current kept); `GET /auth/sessions`; `DELETE /auth/sessions/:id` → 204. `PATCH /auth/me { trainerName?, country?, anonymousRankings? }` (at least one field, else 400 `invalid_body`) → `{ user }`; a new `trainerName` also renames the trainer inside the game doc (bumps the version, emits `game`).

- **Name and country lock (30 days).** `PublicUser` carries `nameChangedAt` and `countryChangedAt` (epoch ms of the last change, `null` = never changed since sign-up), stored in `users.trainer_name_changed_at` / `users.country_changed_at` (nullable `timestamptz`; migration `0003_account_locks_privacy`, so existing accounts start with `null` and their first change is free). Constants `NAME_LOCK_DAYS` and `COUNTRY_LOCK_DAYS` (30) in `src/game/protocol.ts`.
  - A *change* is a value different from the current one (country compared after upper-casing, name after trimming). Sending the current value is a no-op: it never fails, never starts a lock and never moves a timestamp.
  - A change is allowed while `now >= lastChange + 30 days`; otherwise **409** `name_locked` or `country_locked` with `{ error, unlockAt }` (`unlockAt` = last change + 30 days, epoch ms). Each field has its own lock.
  - The request is all-or-nothing: if any change in it is locked, nothing is applied (not even `anonymousRankings`). With both locked, `name_locked` is reported.
  - The check runs inside one transaction after `select … for update` on the user row, so two concurrent changes cannot both pass. `deps.clock()` is the time source.
  - `DEV_TOOLS=1` ignores the locks (same as the time-zone lock in `src/game/actions.ts`); a real change still stamps the timestamp.
- **`anonymousRankings`** (boolean, `users.anonymous_rankings`, default `false`, no lock) is returned in `PublicUser` by register, login, `GET /auth/me` and the PATCH response. See Leaderboard for what it hides.

Game: `GET /game` → `GameSnapshot`; `POST /game/action` with a `GameAction` → `ActionResponse` (`{ doc, version, serverNow, result }`). `serverNow` is the game time used (the dev clock when `x-dev-now` is honored).

- **`createPlayer`** takes no `trainerName`: the server passes the account's trainer name to the reducer (`ActionEnv.trainerName`).
- Reducer error codes (409): engine errors (`session_active`, `invalid_duration`, `empty_team`, `ThrowError`, `ChargeError` incl. the new `already_has_status`, `BoxError`, `UseItemError`, mission errors, `invalid_starter`, `no_active_session`, `invalid_times`) plus `no_player`, `player_exists`, `no_session` (pause/resume/cancel/claim/markNotified without a session, startBreak with no session yet), `paused` (claim while paused), `not_finished` (claim before `endsAt`), `already_finished` (pause after `endsAt`), `no_encounter` (nextWave/finishWaves without waves), `no_break` (endBreak), `already_claimed` (startBreak twice for the same session), `session_active` (startBreak during a session), `session_active_elsewhere` (database already holds an active study session for the user).
- `pause` while paused and `resume` while running are idempotent (200, no change but the version still bumps). `dismissResults` and `skipBreak` always succeed.
- `devFinishNow` is not an action: advance the dev clock (`x-dev-now`) past `timer.endsAt`.
- `claim.devFocusLabel` is ignored unless DEV_TOOLS=1 (then no screenshot labels = "no permission" focus value).
- `claim.soundProfile` (optional) `{ silence, music, voice, noise }`: microphone shares measured in the browser (audio never leaves the device). Each 0–1, sum ≤ 1.05, otherwise 400 `invalid_body`. Passed to `completeSession` in every mode (Flying/Psychic conditions, wild types).
- **`start`** looks up the real weather (Open-Meteo, no API key) and the reducer stores it on `activeSession.weather`; `claim` uses that for Fire/Water/Ice. Source: `profile.location` (a ~0.1° cell rounded by the client and again by the reducer; sent straight to the forecast API, no geocoding), else `profile.city` (geocoded). The lookup waits at most 2 s (a slower one keeps going and fills the cache for the next start); results are cached 30 min per cell / per city, failures 5 min (in memory only). Nothing detected → `weather: null` (no manual fallback). Group starts run the same lookup for each invitee, which is why the rounded cell lives in the profile instead of being sent with `start`. Rule shared in `src/game/weather.ts` (`resolveSessionWeather`). Tests inject a fake `fetch` (`createApp({ fetch })`).
- **`updateProfile.patch.location`** `{ lat, lon } | null` (lat −90…90, lon −180…180, else 400): only the rounded cell is stored; null clears it. No cooldown for location or city.
- **`setWeather`** (manual weather) is a dev action: 403 `dev_disabled` without DEV_TOOLS=1. With DEV_TOOLS=1 `profile.weather` overrides the detected weather; without it, it is ignored everywhere (also in old saves that still carry one, including `claim` of a legacy session without `activeSession.weather`).
- Week keys are the engine's (`weekKeyOf`: the local Monday, e.g. `2026-11-02`), month keys `2026-11`.

Friends: `GET /friends` → `{ friends: FriendSummary[] }` (accepted + incoming + outgoing, oldest first); `POST /friends/request { friendCode }` → 201 `{ userId, status: 'outgoing' | 'friend' }` (code is case-insensitive, spaces/dashes ignored; an inverse pending request is accepted directly); `POST /friends/:userId/accept` → 204 (only the addressee); `DELETE /friends/:userId` → 204 (reject, cancel or unfriend).

Weather: `GET /weather` → `WeatherResponse` `{ city, location, detected: { weather, place, via: 'location' | 'city', fetchedAt } | null, weather, source: 'detected' | 'manual' | 'none' }` (`manual` only with DEV_TOOLS=1; `place` is null for a location) — what a session started now would use (same cache and rule as `start`). For Settings and the conditions preview.

Leaderboard: `GET /leaderboard?scope=global|country|friends&period=week|month` → `LeaderboardResponse`. Only rows with points > 0. Ties share a rank (competition ranking: 1, 2, 2, 4), listed by who reached the score first. `mine` is null when the caller has no points in that period.

Privacy (`anonymousRankings`): in the `global` and `country` scopes a row of a user who turned it on has `trainerName: null` (the client shows "Anonymous trainer"), unless it is the caller's own row (`me: true`), which always carries the real name. `mine` follows the same rule, and the `friends` scope never hides names. Every row has `anonymous: boolean` (the user's setting even when the name is shown, so the caller's own row can say it is hidden). Only the name is masked: `userId`, `country`, points, league and the leader species stay in the row.

Where else a trainer name reaches another user: `GET /friends` (the name of an accepted friend, of someone who sent you a request, and of the owner of a friend code you just requested) and study groups (host and members/invitees in `StudyGroupView` and the `group` SSE event, invitations are friends-only). These are not public contexts, so they ignore `anonymousRankings`.

### Study groups ("Estudiar con amigos")

Tables `study_groups` (lobby → started / ended), `study_group_members` (one row per user who started a session in the group: `session_id`, `joined_at`, `ends_at`, `left_at`, `left_reason`) and `study_group_invites` (`pending | accepted | declined | joined | failed`). Migration `0001_study_groups`.

- `GET /groups` → `GroupsResponse { current, invites, serverNow }`: `current` = the group of my running session, else the lobby I host or accepted; `invites` = pending invites I can still answer.
- `POST /groups { minutes, friendIds (1–7 uuids) }` → 201 `StudyGroupView` (lobby, expires in 30 min). 409 `no_player`, `session_active`, `already_in_group`, `not_friends`, `cannot_invite_self`, `group_full` (8 people).
- `GET /groups/:id` → view (participants only, else 404).
- `POST /groups/:id/invite { friendIds }` (host; lobby or a started group someone is still in). Declined/failed invitees are asked again.
- `POST /groups/:id/accept`: lobby → `accepted`; started → **late join**: the server starts the caller's session now (same minutes) and records the member row. 409 `session_active`, `already_in_group`, `group_ended`, `invite_closed`, `not_friends`.
- `POST /groups/:id/decline` → 204.
- `POST /groups/:id/start` (host): host and every accepted invitee start a session at the same instant (each in a savepoint; an invitee who cannot start → `failed`, the rest go on). 409 `not_host`, `group_ended`, or the host's own start error.
- `POST /groups/:id/leave` → 204: lobby host → disband; invitee → declined; started member → out of the group, session continues solo.
- Hooks in the game action pipeline (`runGameAction`): `pause` and `cancel` (and any end of the session) close the member interval (`left_reason` `pause` / `cancel` / `finished` on claim); a solo `start` drops the user's open lobbies. **No re-joining.**
- **Claim**: `friendOverlap` = time of my in-group interval during which at least one other member was in theirs ÷ my session minutes (`src/game/group.ts`), passed to the reducer as `ActionEnv.friendOverlap` (never from the client) and stored in `SessionResult.friendOverlap`. Fairy multiplier = `1 + (fairy − 1) × friendOverlap`.
- Rate limits per user: create + invite 20 / 15 min; other group writes 120 / 15 min.

### Maintenance notices

Informational banner for planned downtime. Table `maintenance_windows` (`starts_at`, `ends_at`, optional `note`; migration `0002_maintenance_windows`). **Informational only**: the server never blocks or slows requests during a window, and nothing starts or stops by itself. Actually stopping the server (deploy, `docker compose stop`, database work) is still manual; the notice just tells players when to expect it.

- `GET /announcements` (public: no session, `Cache-Control: no-store`) → `AnnouncementsResponse { maintenance, serverNow }`: windows with `ends_at` in the future (upcoming or running), oldest start first, each `{ id, startsAt, endsAt, note }` (epoch ms, UTC). `serverNow` lets the client correct its clock skew.
- Admin API, for a signed-in user with role `admin` (session cookie) **or** the deprecated `Authorization: Bearer <ADMIN_TOKEN>` (see *Roles and admin access*):
  - `GET /admin/maintenance` → `{ items, serverNow }`: the same windows as the public list plus `createdAt`.
  - `POST /admin/maintenance { startsAt, endsAt, note? }` → 201 `{ item }`. `startsAt`/`endsAt` are integer epoch ms with `endsAt > startsAt`, `endsAt` in the future and a window of at most 14 days; `note` is trimmed (empty = none) and at most 280 characters. Otherwise 400 `invalid_body` (+ `fields`). At most 20 windows that have not ended: 409 `too_many`.
  - `DELETE /admin/maintenance/:id` → 204 (404 `not_found` for an unknown or malformed id).
- Who may call it: with an `Authorization` header the request is a token request; without one, a session cookie is resolved and the user must be `admin` (403 `forbidden` otherwise; per-user limit below). Creating and deleting are written to `admin_audit` in the same transaction (`maintenance.create` / `maintenance.delete`).
- Token checks run in this order: `ADMIN_TOKEN` unset → 404 `admin_disabled`; rate limit → 429 `rate_limited`; token → 401 `unauthorized`. The token is compared in constant time (sha256 of both sides + `timingSafeEqual`). Limit: 10 admin requests / 15 min per client IP (set `TRUST_PROXY=1` behind a proxy), counted on every request and cleared by a valid token, so a legitimate admin is never locked out.
- The CSRF guard still applies to `POST`/`DELETE`: send `Origin` (from `APP_ORIGIN`) and `Content-Type: application/json`.

```bash
H=(-H "Authorization: Bearer $ADMIN_TOKEN" -H "Origin: https://pokefocus.example" -H "Content-Type: application/json")
# Schedule: Friday 2026-11-13 02:00-03:00 UTC
curl "${H[@]}" -X POST https://pokefocus.example/api/admin/maintenance \
  -d "{\"startsAt\": $(date -u -d '2026-11-13 02:00' +%s)000, \"endsAt\": $(date -u -d '2026-11-13 03:00' +%s)000, \"note\": \"Database upgrade\"}"
curl "${H[@]}" https://pokefocus.example/api/admin/maintenance            # list (ids)
curl "${H[@]}" -X DELETE https://pokefocus.example/api/admin/maintenance/<id>   # cancel
```

### Roles and admin access

Migration `0005_admin_roles_audit`: `users.role` (`player` default | `support` | `admin`, check constraint), `auth_sessions.elevated_until` and the `admin_audit` table. `PublicUser.role` is returned by `/auth/*` so the client can show the admin link; the server re-reads the role from the database on every request, so a demotion applies at once.

- **Guards** (`server/http.ts`): `requireRole('support'|'admin')` after `requireAuth` (403 `forbidden`; order player < support < admin) and `requireElevated(deps)` for sensitive actions (403 `elevation_required` unless the session's `elevated_until` is in the future).
- `GET /api/admin/me` (support+) → `{ role, elevated, elevatedUntil, serverNow }`.
- `POST /api/admin/reauth { password }` (support+): verifies the password with the login's scrypt hash and sets `elevated_until = now + 30 min` **on the current session only**; answers like `/me`. Wrong password: 403 `wrong_password`. Limit 5 wrong guesses / 15 min per user (cleared by a right one). Audited as `admin.reauth`.
- **Rate limit**: every admin request of a signed-in user counts against `adminUser` (600 / 15 min per user, 429 `rate_limited`). `Cache-Control: no-store` on all `/api/admin/*`.
- **Audit** (`server/admin/audit.ts`): `audit(tx, c, { action, targetType, targetId, before, after, note })` inserts into `admin_audit` (`actor_id` or `actor_label`, `ip`, `created_at`) using the caller's transaction, so the change and its record commit or roll back together. Actors: the user (`actor_id`), `token` (legacy token), `system` (start-up promotion), `cli`.
- **Becoming admin** (accounts are created by normal registration; roles are never self-service):
  - `ADMIN_EMAILS=you@example.com` + restart: existing accounts with those emails become `admin` (idempotent; never demotes; audited as `user.role` by `system`). Emails without an account are skipped with a warning: **register first, then restart** (the email is not verified, so never list one that nobody trusted owns).
  - CLI: `npm run admin:role -- you@example.com admin` (roles `player|support|admin`; reads `.env`; audited as `cli`). With the embedded PGlite the directory cannot be shared with a running server: stop it first (PostgreSQL has no such limit).
- The UI (`#/admin`) uses the signed-in session when the user is `admin` and falls back to the token form otherwise.

### Web Push

**Why.** The page shows the end-of-session notification itself (the leader tab, then `markNotified` sets `timer.notified = true`). But a browser may freeze a hidden tab (Chrome Memory/Energy Saver): then nobody notifies, the player comes back after the claim window and gets the late-claim multiplier. So the server also pushes a notification through the browser's push service (FCM, Mozilla autopush, Apple, WNS) as a **fallback**. The claim window itself does not change.

**Rule** (contract in `src/game/protocol.ts`, code in `server/push.ts`). `runDue()` runs every 15 s (`server/index.ts`, only with VAPID keys) and pushes a session when all hold:

- the player has at least one row in `push_subscriptions`;
- `timer.pausedAt` is null and `timer.notified` is not true (the dedupe: a live page has already notified, so the player never gets two notices);
- `now >= timer.endsAt + PUSH_GRACE_MS` (20 s: the page gets the first chance) and `timer.endsAt > now - PUSH_MAX_AGE_MS` (30 min: no stale pushes after downtime);
- nothing was sent for `(user, sessionId)` yet. `push_sent` (PK `user_id, session_id, kind`) is claimed with `INSERT … ON CONFLICT … RETURNING` before sending, so overlapping runs and restarts send at most once.

The candidates come from one SQL query over `player_docs.doc->'timer'` with `EXISTS (push_subscriptions)` (users without subscriptions cost nothing); the doc is re-read and the rule re-checked right before claiming. Payload (`PushPayload`, JSON, localized by `player.profile.locale`, default English): `{ type: 'session-end', title, body, tag: 'pokefocus-session', url: '/' }`, body built from `claimWindowMinutes` of the game config. Sent with `TTL` = the claim window (a later push is useless) and `Urgency: high`, a 10 s deadline per subscription, all subscriptions in parallel. Push-service answers: 404/410 → the subscription is deleted; success → `last_success_at`; if **every** delivery failed transiently (network, timeout, 429, 5xx) the claim is released (`sent_at = NULL`) and the next tick retries, at most 3 attempts in total (`push_sent.attempts`). Other errors (400/401/403/413) keep the subscription and do not retry.

**Setup.** `npm run vapid` prints `VAPID_PUBLIC_KEY=…`, `VAPID_PRIVATE_KEY=…`, `VAPID_SUBJECT=mailto:you@example.com` (edit the subject); paste them into `.env` (or the compose environment). Generate the pair once: new keys invalidate every existing browser subscription. Keys and endpoints are never logged.

**Endpoints** (all need the session cookie; `POST`s need `Origin` + JSON like every other write):

- `GET /push/config` → `PushConfigResponse { enabled, publicKey }` (`Cache-Control: no-store`). Without VAPID keys: `{ enabled: false, publicKey: null }`.
- `POST /push/subscribe { endpoint, keys: { p256dh, auth } }` (the browser's `PushSubscription.toJSON()`) → 204. Upsert by endpoint: an endpoint known for another account moves to the caller (same browser, different login). At most 10 per user → 409 `too_many` (re-subscribing an own endpoint does not count).
- `POST /push/unsubscribe { endpoint }` → 204; removes only the caller's own row; idempotent.
- `POST /push/test` → 200 `{ sent }`: sends a `type: 'test'` payload to every subscription of the caller (409 `no_subscription` with none). Use it to check the whole chain on a real browser.
- Errors: 404 `push_disabled` (subscribe / unsubscribe / test without VAPID keys), 400 `invalid_body`, 409 `too_many` / `no_subscription`, 429 `rate_limited` (subscribe + unsubscribe: 30 / 15 min per user; test: 5 / h per user).

**SSRF guard.** The server only POSTs to real push services. An endpoint must be an `https:` URL of at most 2048 characters, without credentials, on port 443, and its host must equal or end in `.` + one of: `googleapis.com` (FCM: `fcm.googleapis.com`), `push.services.mozilla.com` (`updates.push.services.mozilla.com`), `push.apple.com` (`web.push.apple.com`), `notify.windows.com` (`*.notify.windows.com`). So `fcm.googleapis.com.evil.com` and `evilgoogleapis.com` are rejected. `p256dh` must decode (base64url) to a 65-byte uncompressed P-256 point and `auth` to 16 bytes.

**Single instance.** The scheduler runs in the process (no overlapping runs in one process). Two instances on one database would still send at most once (`push_sent`), but like the event bus and the rate limiter this assumes one server.

**Service worker.** In production `/sw.js` (from `public/sw.js`, copied to `dist/` by Vite) is served with `Content-Type: text/javascript` and `Cache-Control: no-cache`, and a missing `/sw.js` is a 404, never the SPA `index.html`.

Testing locally: set the three `VAPID_*` in `.env`, enable notifications in Settings, then `POST /api/push/test` (or the Settings button). For the fallback, start a short session, close or freeze the tab (`chrome://discards`) and wait for `endsAt` + 20 s. Push services need a reachable https origin or `localhost`.

### Server-Sent Events

`GET /api/events` (use `new EventSource('/api/events')`; same-origin, the cookie goes along). Each event is an unnamed message (`onmessage`) whose `data` is a JSON `ServerEvent`:

- `{ type: 'game', version }` after every successful write of the user's doc (from any tab, including the one that made it — compare `version` and ignore what you already have).
- `{ type: 'friends' }` to both users on request / accept / remove.
- `{ type: 'group', groupId, kind, userId, trainerName, reason? }` to every participant of a study group on invite / accept / decline / start / join / leave / disband / failed (`kind`); `reason` on `leave` (`pause | cancel | leave | finished`). Refetch `GET /api/groups`.
- `{ type: 'logout' }` to the connections of a revoked session (logout-all, password change, DELETE /auth/sessions/:id), then the stream closes.

The stream starts with `retry: 5000` and sends a `: ping` comment every 25 s. 401 if there is no session.

## Security

- **Passwords**: `crypto.scrypt` N=2^15, r=8, p=1, 64-byte key, 16-byte random salt, stored as `scrypt$N$r$p$salt_b64$hash_b64`, compared with `timingSafeEqual` (maxmem raised to 64 MiB because N·r·128 = 32 MiB hits Node's default). 8–128 chars, NFKC-normalized. Never logged.
- **No account enumeration on login**: unknown emails are verified against a random dummy hash, same error `invalid_credentials`. (Registration does say `email_taken`; it is rate-limited.)
- **Sessions**: 32 random bytes (base64url) in the cookie, only `sha256(token)` in `auth_sessions`. New token on every login/registration. Cookie `pf_session`: `HttpOnly; SameSite=Lax; Path=/; Max-Age=30d`, `Secure` in production. Sliding expiry: a request more than 24 h after `last_seen_at` pushes `expires_at` to now + 30 d and re-sends the cookie. Expired rows are deleted hourly.
- **CSRF**: `Origin` must be in `APP_ORIGIN` for every non-GET/HEAD request, JSON content type required, plus `SameSite=Lax`.
- **Brute force**: in-memory fixed windows — login 10 / 15 min per IP and 5 / 15 min per email (attempts; a successful login clears the email counter), register 5 / h per IP, admin API with the legacy token 10 / 15 min per IP (a valid token clears it) and 600 / 15 min per signed-in staff user. Single process only; behind a proxy set `TRUST_PROXY=1`.
- **Web Push**: endpoints restricted to known push-service hosts (https, port 443, no credentials, ≤ 2048 chars); VAPID private key only in the environment; keys and endpoints never logged.
- **Admin API**: staff are accounts with role `support`/`admin` (session cookie, CSRF Origin check, per-user rate limit, sudo mode via password re-entry for sensitive actions, every mutation audited). The deprecated `ADMIN_TOKEN` (≥ 24 chars) only opens maintenance notices, compared with `timingSafeEqual` over sha256 digests; it never touches player data.
- **Authority**: time, rolls, points and captures are decided by the server. `x-dev-now` / `x-dev-seed` and `dev*` actions only with `DEV_TOOLS=1`, never in production.
- **Concurrency**: every action runs in one transaction: `SELECT … FOR UPDATE` on `player_docs` → `applyAction` → `active_study_sessions` / `league_scores` updates → `version + 1`. Two tabs never overwrite each other.
- **Headers**: Hono `secureHeaders()` (HSTS, nosniff, frame options, COOP/CORP, no referrer…). Body limit 64 KB. All SQL through Drizzle (parameterized).

## HTTPS in production

Cookies are `Secure` in production, so the site must be served over HTTPS (browsers do accept Secure cookies on `http://localhost` for local tests). Put a reverse proxy in front of the app; with [Caddy](https://caddyserver.com) (automatic Let's Encrypt certificates):

```caddyfile
pokefocus.example.com {
	encode zstd gzip
	reverse_proxy localhost:8787 {
		# SSE: send events right away
		flush_interval -1
	}
}
```

Then run the app with `APP_ORIGIN=https://pokefocus.example.com` and `TRUST_PROXY=1` (and do not publish port 8787 to the internet: bind it to `127.0.0.1:8787:8787` in `docker-compose.yml` or put Caddy in the same compose network).

## Limits / future work

- The event bus, the rate limiter and the Web Push scheduler live in the process: run a single instance (or move them to Postgres `LISTEN/NOTIFY` / Redis / a job queue).
- No email verification or password reset yet (no mail sending).
